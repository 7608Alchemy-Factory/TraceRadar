# 联网搜索接入后的评测设计（2026-11-22）

## 对齐依据与实验边界

Proposal 第 5 节规定五项能力：Information Relevance、Topic Evolution Accuracy、Event State Update Accuracy、Notification Quality、Evidence Grounding and Trace Consistency。老师的 final report 要求代表性、挑战和失败案例，参考结果或判定规则、指标、公平 baseline 或组件比较、实际结果和局限；记录设置与可变输出；若用 LLM 判分，必须有明确标准和人工检查。报告按五项分别给分子、分母和错例，不用一个总事件数代替效果，也不强行平均五项。

| 实验线 | Agent 输入与目的 | 可以报告 | 不可报告 |
|---|---|---|---|
| A. 固定证据回放 | 冻结文章按阶段可见；保留现有 Replay runner。隔离搜索变量，测读后判断。 | 固定候选池的相关性、Event 边界、状态、通知、溯源。 | 找全互联网新闻的能力。 |
| B. 限定来源联网搜索 | 只给 Topic、批准的域名/来源、时间窗、阶段截止与搜索预算；Agent 自行搜、取全文。 | 已知关键来源覆盖、已裁定候选池的检索表现、发现材料的有效率、噪声和失败案例。 | 对未穷尽网络的“全网 Recall”。 |
| C. 端到端 | 搜索、筛选、更新、通知全部开启。 | 用户可见结果与端到端耗时；错误归因到搜索或后续判断。 | 把 A 与 B 的分数混成一个准确率。 |

同一案例可以用于三线，但 A 使用冻结转述，B/C 使用来源白名单与真实网页；分别编号、记录实验版本，不能把 A 的 fixture 暗中作为 B/C 的检索答案。联网结果不可避免随索引和网页变化：每次保存查询、搜索返回项、抓取到的正文或允许保存的摘录、URL、规范 URL、发布时间及其可信度、抓取时间、正文哈希、页面版本、HTTP 错误和搜索服务标识。网页历史版本不明时，只在实际抓取阶段计入；不得将今天页面的内容放回过去阶段。

Proposal 要求用户批准信息源。评测时保存“Agent 建议的来源”和“用户已批准的来源”两份清单；只有后者可进入正式检索输入。若未来实现动态来源推荐，另报推荐被人工接受的比例及漏掉的关键来源，不把未批准来源偷偷当作 Agent 可用输入。

## 五项指标的可操作判定

| Proposal 指标 | 数量层 | 内容层 / 判定规则 |
|---|---|---|
| Information Relevance | 在**已裁定候选池**上计 TP/FP/FN、precision/recall/F1；另报未裁定、抓取失败、重复和覆盖的独立来源数。 | 人工判文章是否落在 Topic 范围、是否只是转载、片段是否与正文一致。开放搜索的“已知关键来源覆盖率”以事先列出的已知来源为分母，明确不是全网召回。 |
| Topic Evolution Accuracy | 各阶段预期/实际 Event 数、误建/漏建/拆错/合错、证据到 Event 的归属对数。 | 先按边界和证据人工对齐 Event，再判同一事件的连续更新；MCD-03 一篇文章可对应两个 Event，不能拿文章数当事件数。 |
| Event State Update Accuracy | 各阶段必需 claim 的命中/遗漏/矛盾数、禁止断言数、状态转移数；时间触发与证据触发分开。 | 看 `current_status`、事实、日期条件、历史版本、未知截止日和阶段 `as_of`。同义表达可通过人工或有量表的 LLM judge 判断；不能用字符串包含或 Event 数代替。 |
| Notification Quality | 按 `milestone_id` 对齐，计 immediate/digest/record_only 的混淆矩阵、重大进展漏报和重复提醒。 | 同一进展多篇报道只应对应适当提醒；固定用户偏好，核查理由与实际动作。 |
| Evidence Grounding and Trace Consistency | 统计 claim 中存在、在阶段可见且归属正确的引用比例，缺引/越时引用/不存在引用数，以及 Run/Transition/Notification 链路断裂数。 | 人工抽查引用的**原文是否真正支持**该 claim，尤其数字、来源归属、传闻、冲突、历史页面。仅有有效 evidence ID 不等于事实有依据。 |

数量仍要评：它给 TP、FP、FN 和成本/覆盖的分母，能发现漏建、过度拆分、重复通知等。数量必须在**实体和里程碑对齐之后**解释；“5 个 Event 对 5 个预期”仍可能全部配错，故不得单独报通过。内容判分在同一张逐阶段核验表里完成，给每条 claim 标 `supported / missing / contradicted / unclear`，每个事件边界标 `correct / merged / split / missing / extra`，状态与通知分别标记。`unclear` 不强算对错，进入人工裁定。

## 联网搜索的候选池与参考答案

1. 运行前固定 Topic、批准来源、时间窗、时区、搜索/抓取预算、查询次数、最大结果数、模型与提示版本；不把 Ground Truth 或已知 URL 清单给 Agent，除非实验明确是“已批准 URL 监测”。
2. 预先列出**已知关键进展与来源**，用于已知覆盖率。运行后将人工检索、Agent 检索及一个独立检索途径的结果合并，按规范 URL 和内容哈希去重；标注合并池中的相关性、Event、claim、来源版本及发现路径。未标注项记 `unjudged`，不自动归为 FP。
3. 新发现的有效文章进入下一版候选池和 Ground Truth；已公布的一轮结果保留原池与哈希，不事后扩充该轮分母。历史页面无法复原则标版本不确定，排除历史召回和小时级时效评分。
4. 同时报告搜索失败、不可访问页面、缺发布时间、源站更新、搜索预算用尽以及人工未裁定比例。若未裁定比例高，不报精确检索分数，只给已裁定部分与上下界/个案。

## 公平比较、可变输出与人工核验

建议至少保留一个简单 baseline：相同来源白名单、时间窗、搜索预算和候选池下，“检索 + URL/哈希去重 + 每篇摘要/摘要通知”，不做跨篇 Event 状态追踪；并做组件对照：A 固定回放与 C 端到端、相同候选材料下启用/关闭关联或去重。比较时保持模型、提示、温度、用户通知偏好和网络可用时间尽量一致；记录不同预算/失败，不把模型或搜索服务更换带来的差异归给 Agent 架构。若基线未实现，报告中明确写未完成，不用假想数字。

每组至少记录模型 ID、API 服务、提示版本、温度/seed（若服务支持）、搜索服务/查询、来源白名单、抓取与回放截止、尝试次数、超时、代码提交和所有输入/标注哈希。正式结果建议每条件重复至少 3 次，报告每次原始结果、均值与范围，并保留失败样本；搜索结果跨时段不可视为完全同分布。挑战例须包含一文多 Event、重复报道、谣言/冲突、未知截止日、单 URL 改写和来源缺失；失败例要区分检索、抓取、模型契约、业务判断与系统功能缺口。

如引入 LLM judge，只让它对已对齐的单条 claim 或边界给出标签、支持的证据片段和理由，采用固定 rubric：事实主语、动作、条件、数字/日期、来源归属均正确才算 `supported`；部分正确记 `unclear`，与证据冲突记 `contradicted`。Judge 不读取 Agent 私有推理，不修改标准答案。由人复核**全部**负例、`unclear`、跨来源冲突和至少一部分正例；记录复核比例、分歧与最终裁定。正式报告不能仅用 judge 原始输出作准确率。

## 脚本落地顺序

- **现在已可用：** `scripts/run_benchmark.py` 保留固定回放与原始报告；`scripts/build_review_sheet.py` 从已有 `report.json` 生成逐阶段对照表，列出预期 claim/状态/里程碑、实际事实/通知、结构性引用检查和待人工勾选项，不再只看数量。它不进行语义自动判分，也不请求模型。
- **联网功能合并后：** 在 Runtime 增加可查询的搜索/抓取 trace 与候选池导出；新 runner 从 Topic/来源白名单/时间窗启动真实搜索，保存网络快照及版本，不读取 Ground Truth；评测侧再对池标注并计算检索指标。保留固定回放回归门，定位端到端下降来自检索还是判断。
- **评分器下一步：** 依据人工裁定表计算五项分子/分母、错例和跨次统计；对无法确定的 Event 配对、语义 claim 与网页历史可见性保留人工标签，不伪造自动分数。
