# TraceRadar 后续开发 prompts

每段可以独立交给组员或编码代理。开始前核对当前 Git 分支、工作区和接口版本。涉及评测数据时使用独立 SQLite 数据库，保留个人工作区和模型配置。

## 1. 运行记录与部分失败

> 从 `frontend-1121` 开始，完善 TraceRadar 的「运行记录」。目标是让使用者在两次点击内找到一次检查有没有实际更新、失败发生在哪一步、哪份证据受影响。
>
> 先阅读 `backend/app/orchestration.py`、`backend/app/repositories.py`、`docs/api_contracts.md` 和前端的 Run、Trace 类型。逐项核实 `fetched`、`committed`、`no_change`、`skipped`、`irrelevant`、`review`、`errors`、`unprocessed` 的语义。区分旧记录字段缺失与计数为 0。若 `skipped` 混合多种原因，使用已记录的 Trace 原因进一步解释，保持总数与后端口径一致。
>
> 改进运行详情的总结与证据入口。展示运行状态、已提交的更新、已判断无变化、待审、实际失败和后续未处理。必要时显示证据标题、阶段、错误类别和重试次数，能够打开已入库的证据。仅在后端记录了证据身份时为未处理条目显示名称。保留用户选中的历史运行，同时后台轮询可继续更新当前运行。
>
> 为新增界面补齐简体中文、繁体中文和英文文案，检查浅色、深色、桌面与手机。用独立测试数据库覆盖无更新、重复回放、部分失败、队列仍在运行、历史记录字段不全。使用可控的模拟响应复现服务失败。交付界面、验证结果及任何确实需要的 API 增量。

## 2. 评测错例复核与可复现记录

> 与成员 A 一起，从 `evaluate` 的运行记录和 Ground Truth 草稿挑三个错例。分别选择本应更新却被标为佐证的材料、事件归属不正确的材料，以及出现冲突需要人工核查的材料。如果报告没有保留足够的证据或模型输出，注明缺失字段，并在隔离数据库中定向重现。以经独立复核的人工标签为准。
>
> 每个错例记录提交哈希、语料版本、案例 ID、阶段和 `as_of`、证据 ID、模型 ID、提示词版本、生成参数、耗时和重试次数。保留当前输入、人工期望、模型结构化判断、StateManager 的接受／拒绝原因、最终状态与通知。记录公开的结构化决策和必要错误信息，实验输出保持凭据与私有推理不入报告。
>
> 把问题分到来源／证据、模型契约、事件归属、状态提交、基础设施和功能缺口。分别统计未处理、错误、成功提交及无变化。确认模型既标记 `confirmation` 又提供新事实时，新校验是否拦截，以及有重试机会时能否修正。以同一数据、同一截止时间、同一提示和同一模型对比改前改后，再记录其他模型的结果作为独立实验。
>
> 输出可复现命令、最小复现输入、预期与实际对照表、建议归属和复验结果。由 A 决定是否修订标签或冻结版本。正式模型效果留待冻结标签和完整评分后报告。

## 3. 一条证据关联多个 Event 的接口与工作台

> 与 B、C、A 先完成一页方案，再用独立分支实现。用香港麦当劳案例的同一篇公告支持套票和茶饮两个独立活动作为验收用例。两个活动分别有状态、期限和通知，共用一条 Evidence 及其来源引用。
>
> 查清 `Assessment`、`StateManager`、`event_evidence`、状态历史、通知幂等键、Run 计数、OpenAPI 和前端视图现在如何假设一证据一关联。提出最小的向后兼容契约，例如单条 Evidence 保持一个评估记录，其中包含按目标 Event 分开的判断和更新列表。明确一个关联失败时的事务与重试策略、每事件的版本校验、通知去重键，以及旧记录与单事件客户端的兼容口径。与 B 确认契约后再开始接口迁移。
>
> 工作台原型覆盖两头导航。Event 档案展示关联证据；证据详情列出支持、冲突或待审的多个 Event；审核动作明确绑定到当前目标 Event。用一个案例验证同一次变动只提醒一次，并可从每个状态变更追溯到同一个 `evidence_id`。将时间驱动的自动失效作为单独能力验收。
>
> 交付契约变更、示例请求与响应、旧数据兼容说明、桌面和手机验收，以及测试。测试至少覆盖原有单关联、同证据支持两事件、重跑幂等、跨 Topic 拒绝、其中一个目标版本冲突和人工审核。A 同步确认 benchmark 如何逐事件计分。
