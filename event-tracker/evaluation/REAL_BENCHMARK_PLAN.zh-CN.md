# 真实案例 Benchmark 整理方案（讨论版 v0.2）

日期：2026-11-18。负责人：成员 A。本文只规定整理与评测方法；具体候选主题另行讨论。已完成的虚构案例 `cedar_patch_v1` 用于检查流程，不代表真实世界准确率。

## 1. 两条实验线

| 实验 | 输入 | 可以评估 | 不应宣称 |
|---|---|---|---|
| 固定语料回放（主评测） | 事先收集并核验的有限材料，按发布时间分阶段交给 Agent | 给定材料后的相关性、Event 归属、状态演化、通知与证据溯源 | 找全互联网报道或真实检索召回率 |
| 限定来源的开放检索（补充） | Topic、来源白名单和时间窗，由系统自行获取材料 | 已核查输出的有效比例、已知关键进展覆盖、噪声与漏发现案例 | 对全网新闻的完整召回率 |

先完成固定语料回放；连接器稳定后再做开放检索。两种结果分开报告，未标注文章不能自动算作错误或正确。TREC 也强调相关性标注必须与指定文档集合配套；大规模检索通常只标注合并后的候选池：[TREC 相关性标注](https://trec.nist.gov/data/reljudge_eng.html)、[TREC pooling 说明](https://trec.nist.gov/howto.html)。

标准答案统一使用 [`templates/ground_truth.template.json`](templates/ground_truth.template.json) 的 v2.0 结构；字段解释和当前代码能力边界见 [`templates/README.md`](templates/README.md)。案例输入与 Ground Truth 严格隔离。

## 2. 每个案例的制作步骤

1. **Case Brief**：先写 Topic 目标、追踪时间窗与时区、来源范围、允许的材料类型，以及 Event 边界。写清何时是同一 Event 的后续、何时要新建 Event、何时属于 Topic 外信息。
2. **来源台账**：每条材料保存稳定 ID、原始 URL、发布者、标题、最初发布时间、抓取时间、核验状态、短摘要或必要摘录、内容哈希和网页版本。搜索结果片段不等于原文。保存全文前核对使用条件。
3. **候选池**：优先官方原始资料，再补独立报道、转载、可能冲突的信息及相关但无关的材料。第一版建议约 8–15 条、2–4 个回放阶段；不足则如实报告，不为凑数制造进展。
4. **独立标注**：逐条标相关性、重复、Event key、新颖性、应否更新、通知和支持事实；逐阶段标当前状态、关键事实、支持证据及不得断言的内容。第二位标注员独立核对一部分，记录分歧与裁定。Agent 输出不得充当标准答案。
5. **冻结版本**：记录输入、标准答案和配置的版本与哈希。修改产生新版本，不覆盖已报告实验。运行时只向 Agent 提供案例输入；标准答案仅由评测器读取。

网页可能在原 URL 持续改写。必须尽可能恢复每个阶段**当时可见的版本**；最终页面不能整体投入早期回放。若旧版本不可得，该页只用于最终阶段，或换用分别发布的历史公告。

## 3. 持续追踪 Topic、多个 Event 与过期

持续追踪的 Topic 可包含多个独立事项。例如“某品牌在香港的活动”下，能独立开始、结束或更新的活动各为一个 Event；一篇文章可以为多个 Event 提供证据。同一新品系列的关联优惠也可以归一个 Event，但各优惠的适用条件和期限须分别保存。不能把新活动覆盖到旧活动上，也不能把每篇转载都建成新 Event。相同起始日期只可作为辅助线索，不能单独决定 Event 边界。

活动到期有两种不同情形：

- **新证据引起状态变化**：官方宣布延期、提前结束或取消，系统读取新公告后更新。
- **时间引起状态变化**：已知截止日到来，系统应把活动标为失效，即使没有新文章。

第二项需要定时检查或回放时的时间驱动规则。仅把回放的 `as_of` 设在截止日之后，并不保证当前 Runtime 会自动更新状态。评测要先检查实现是否支持，再分别报告“是否正确提取截止日”和“是否按截止日更新为失效”。未实现的能力列为功能缺口，不混进内容判断准确率。

## 4. 新发现文章与来源多样性

如果 Agent 找到台账外的文章，先标 `unjudged`，核对来源、发布时间、原文、事实和重复关系。符合范围的材料进入候选池**下一版本**；当前已冻结实验保持不变。开放检索可把人工搜索、Agent 结果和另一种检索方式的结果合并去重后再标注，但仍需报告候选池来源与未标注数量，不能把已知材料覆盖率说成全网 Recall。

固定语料可以混合官方、独立研究、媒体及干扰项。来源数量本身不是评分目标；重点是事实能否被当时可见的独立证据支持，以及系统能否识别转载、矛盾和来源局限。来源白名单和时间窗必须在运行前确定。

## 5. 评分与报告

- **相关性**：固定候选池中已裁定材料的 precision、recall、F1；去重另计。未处理或运行失败单列，不算作“不相关”。
- **Event 演化**：将系统 Event 与人工 Event key 按证据归属对齐，计误建、漏建、错归属和阶段性里程碑遗漏。
- **状态更新**：按事实含义、时间条件与证据支持判定，另列错误断言、未核实消息被确认为事实、旧状态错误覆盖。
- **通知**：按新进展而非文章数对齐，计重大进展漏报、一般进展误报和重复提醒；固定并记录用户通知偏好。
- **证据与 Trace**：事实引用应存在、属于该 Topic 且在当时已可见；Run/Trace 与持久化状态及通知一致。

报告每项的分子、分母、分数、未裁定数、失败数和逐案例错例。五项不强行平均为一个总分；固定回放和开放检索不混算。

## 6. A 的交付顺序

先为一个持续追踪 Topic 和一个单事件 Topic 各写一页 Case Brief；建立来源台账，判断是否能形成真实阶段；优先完成资料链最完整的案例，独立标注并裁定；最后冻结版本并接入回放接口。代码集成时间不影响资料整理和标注。
