# CedarDesk 文件预览漏洞：单事件演化 Benchmark v1（草稿）

标准答案现采用统一 v2.0 模板；本文件中的逐条口径仍供人工核对。

这是**完全虚构**的评测案例。CedarDesk、公告、报道和网址均为测试素材，不代表真实产品或事实。目标是测试一个 Event 从调查、确认、临时缓解到补丁发布的连续追踪能力。

## 文件与隔离

- `case.json`：Topic、回放来源和三个截止时间；可交给运行器。
- `../../../fixtures/cedar_patch_v1/all.json`：Agent 可见的九条原始证据；运行时不得读取本目录的标准答案。
- `ground_truth.json`：A 使用的人工答案草稿；仅评测器读取。正式测试前应由第二位标注员独立核对、裁定并冻结版本。

证据以 `(原始 source_id, external_id)` 标识。当前 ReplayConnector 会将不同原始来源映射到一个注册的 replay source，并把原始来源前缀加到运行时 `external_id`，例如 `cedar_vendor:CP-01`。评分时应据此前缀映射，不能依赖运行时生成的 UUID。此处的原始来源是故事的一部分，并不代表实际独立抓取或来源可靠性实测。

## 阅读顺序与阶段答案

| 阶段 | 新出现的证据 | 应有的理解 |
|---|---|---|
| s1_initial | CP-01～03 | 厂商仅在调查；转载不重复建事件；匿名帖子不可当成已证实事实。 |
| s2_confirmed | CP-04～07 | 确认影响版本和触发条件；区分临时缓解与正式补丁；MapleMail 新闻无关。 |
| s3_patched | CP-08～09 | 正式补丁发布是重大里程碑；转载不应再触发相同通知；历史仍可查看。 |

每个阶段只增加新证据，不重置 Topic。开始正式实验时应使用空白 Topic 和数据库状态，按 `case.json` 的 `as_of` 顺序运行，固定模型、提示版本、去重选项和通知偏好。人工审核动作不进入 Agent 主评分。当前 `main` 尚无 replay source 接口；此案例与远端 C/D 开发分支的接口对齐，待分支集成后才能直接回放。

## v1 评分口径

先输出逐项判定，再汇总，不把五项硬合成一个总分。对措辞不同但事实相同的输出做人工语义判定；错误断言单独列出。`ground_truth.json` 是作者草稿，不应直接宣称正式准确率。

1. **相关性**：九条证据逐条判定。CP-05 应排除；CP-02/09 虽重复仍与 Topic 相关。分别报 precision、recall、F1，以及未处理/失败数。
2. **事件演化**：三个阶段都应只有同一个漏洞 Event；CP-01 创建，CP-04/06/07/08 归入该 Event。多建或漏建均记录。运行时 Event ID 与人工 `event_key` 按证据归属对齐。
3. **状态更新**：逐条检查 `claims` 与各阶段 `status`、`must_not_claim`。允许同义表达，但必须保留调查→确认→缓解→修复的时间顺序。CP-03 的未经证实说法不能作为确认事实；CP-06 不能被写成补丁。
4. **通知**：CP-08 应产生一次即时通知；CP-09 不应再产生同一进展的即时通知。CP-01/04/06/07 的普通更新按草稿期望进入 Digest。若系统将重复报道合并处理，按同一变化单元计数，不要求每条文章各有通知。
5. **证据与 Trace**：每个新事实和状态变化应引用在该阶段已出现的相关证据；引用不存在、引用未来证据、引用 CP-05 支撑漏洞事实均记错。Run/Trace 与最终持久化结果应一致。

`novelty=unverified_claim` 是评测侧标签，用来区分未经证实的新说法与已经确认事实之间的真正冲突；它不要求与 Runtime 的 `Assessment.novelty` 枚举逐字一致。`notification=none` 表示不应产生新的通知，不是 Runtime 的通知动作枚举值。

## 冻结前检查

让另一位标注员只看 `case.json` 和证据文件，独立填写相关性、Event 归属、状态与通知；再与本答案比较并记录分歧。完成裁定后更新 `annotation_status`，记录文件哈希和版本号。之后若修改证据或答案，应升版本，不覆盖已报告实验的输入。
